# T3 Craft: thread images and the agent’s browser

Research date: 2026-11-05. Implementation target: Minecraft Java 26.3 / Fabric and T3 Code `v0.1.7-nightly.20261103.4119`, source commit `cefb544af3c98224874419198c0359b652ca3c94` (verified against the supplied clone). This is a source-backed design, not an end-to-end tested implementation. The mod working tree was not changed. Mod inspection used `git show origin/main:<path>` and `origin/feat/t3-mcp-backend:<path>`; `T3McpBackend` exists only on the latter. Decompiled Minecraft classes under `specs/minecraft` were inspected without modification.

## Verdict and recommended scope

- **Thread raster images: feasible now with the legacy environment connection.** Preserve attachment descriptors, fetch signed assets, decode off-thread, and display bounded textures. This includes user images, assistant attachments, tool image outputs, and screenshot outputs actually persisted in the thread. Implement first.
- **Public MCP alone: incomplete.** `t3_thread_read` returns text-oriented timeline items without typed attachment/image descriptors. Public MCP credentials are explicitly rejected outside `/mcp`; they cannot mint legacy asset URLs or browser tickets. A previously minted signed asset URL works without a bearer token, but discovering/minting it is missing. PR #1’s optional legacy connection is the practical bridge.
- **Live agent browser: feasible now through the legacy connection for streamable T3 tabs.** There is already a binary JPEG WebSocket stream, viewport/control events, input forwarding, and human/agent ownership. This is the best match for “the agent’s browser,” and adds no Chromium installation to Minecraft. Ship observe-only first, then explicit Take control.
- **Not every desktop tab is streamable.** The stream looks up server-runtime tabs (including server-runtime tabs backed by an attached desktop page). Pure `runtime:'desktop'` tabs are not generally exposed through this stream. Treat the runtime/capability boundary honestly; do not silently load a duplicate URL and call it a mirror.
- **MCEF: not a release dependency for 26.3.** Apple Silicon is supported by existing MCEF releases, but no published 26.3 Fabric build was found. A separate browser also does not share T3’s page/session. Keep as a future optional experiment, not the zero-setup solution.
- **System browser: feasible fallback**, with separate cookies/page state and localhost reachability caveats.

## 1. Thread data and image retrieval

### Source representations

1. `messages[]` contains conversation messages with `attachments`. Timeline `user_message` has `messageId`, `text`, `attachments`; `assistant_message` has `messageId`, `text`, optional `attachments`, and `streaming`. Use stable IDs to avoid displaying the same message attachment from both projections. `ChatImageAttachment` is `{type:'image', id, name, mimeType, sizeBytes, source?}`. Dimensions are not fields of that descriptor. `source` may contain snapshot provenance/accessibility. File attachments use `type:'file'` and can include non-raster content. IDs are opaque: ordinary stored IDs are a safe thread segment plus UUID, optionally an extension suffix; never infer a URL from the display filename. [S1, S2, S3]
2. Tool results are `dynamic_tool` items: `{id, …, toolName, viewedImagePath?, input, output?, outputOmitted?}`. Recognized images are MCP-style `{type:'image', mimeType, data}` or Anthropic-style `{type:'image', source:{type:'base64', media_type, data}}`. They can be a single block, an array, or `output.content`. The image ordinal is the position in the **filtered recognized-image list**, not the raw content-block index. T3 serves at most eight recognized images, with a 10 MiB decoded-image byte ceiling. These are not `ChatAttachmentId`s; their address is `(sourceThreadId, sourceItemId, imageIndex)`. Port the small bounded extraction logic, not a recursive search through arbitrary JSON. [S4, S5]
3. Normal wire projection deliberately removes tool output bodies and retains compact metadata plus `outputOmitted:true`. Fetch `orchestration.getTurnItem({threadId,itemId,revision?})`, result `{item:…|null}`, when an image-capable tool row becomes visible. Detail output strips base64 but preserves ordered `{type:'image',mimeType}` markers. The signed asset endpoint reads the stored bytes. Do not expect base64 in normal snapshots and do not parse omission as “no images.” For inherited timeline rows use the source thread/item identity, not the viewing thread’s identity. [S5, S6]
4. Agent screenshot tools are not necessarily user attachments. At this tag the important registered browser API is `preview_snapshot` (with `includeImage`, `save`, etc.); do not hard-code an assumed older `preview_screenshot` tool name. `includeImage:true` returns a PNG image block alongside screenshot metadata. Without it the result can contain metadata only; `save:true` can return only `screenshotPath`. A saved path is not a remotely fetchable image URL. Device screenshots and `html_preview` likewise can produce image content. Reuse general tool-image extraction. [S7]
5. `html_render` is **HTML, not a PNG**. Its tool output includes `htmlRender:{attachmentId,title,height,heights?}`; publishing writes an `-html` attachment containing the HTML document. `html_preview` may have generated an earlier PNG, but it is a separate tool result, not a guaranteed thumbnail of the final render. Display an “Interactive HTML” card and Open in browser; a final PNG thumbnail requires an upstream render/capture endpoint or an explicitly created preview tab. Do not feed HTML to `NativeImage`. [S8]
6. Assistant Markdown `![alt](path)` is another route: a remote URL or workspace image reference can exist without an attachment. Recognize actual image syntax outside fenced code. Resolve workspace paths on the T3 host using `media-file`/`workspace-file` asset resources, never read that absolute path from the Minecraft machine. Keep unsupported/unavailable paths visible as links. Do not attach T3 credentials to arbitrary remote image origins.

### Exact legacy flow

“Legacy” here means the mod’s authenticated environment HTTP/WebSocket backend, still using orchestration protocol 2 on this installed release; it does not mean reverting to protocol 1.

1. Read `GET /api/orchestration/threads/:threadId/bounded` with the existing protocol negotiation and `Authorization: Bearer <environment access token>`. The mod’s `T3Api.thread()` and `T3Protocol` already adapt its projection. Other installed endpoints include `GET /api/orchestration/threads/:threadId`, `/transcript`, and `/history`. Do not invent `/attachments/:id` as a download API. [S9]
2. Mint RPC ticket with `POST /api/auth/websocket-ticket/rpc` using that bearer token (no request body). Result `{ticket,expiresAt}`. Existing bare `/api/auth/websocket-ticket` is backward-compatible. Connect `/ws?wsTicket=<encoded-ticket>&orchestrationProtocol=2` using the existing `T3Socket` framing. [S10]
3. Call RPC **`assets.createUrl`**, with one of:

```json
{"resource":{"_tag":"attachment","attachmentId":"…","disposition":"inline"}}
{"resource":{"_tag":"tool-output-image","threadId":"…","itemId":"…","index":0}}
{"resource":{"_tag":"media-file","threadId":"…","path":"relative/image.webp"}}
```

Attachment optional fields: `fileName`, `mimeType`, `disposition:'inline'|'attachment'`, `renderIntent:'mcp-app'`. MIME/filename hints do not grant file access. Result: `{relativeUrl,expiresAt,sourcePath?,imageDimensions?:{width,height},fileRevision?}`. Attachment/tool image minting requires `orchestration:read`; workspace/media/draft-workspace files require `filesystem:read`. [S11]
4. Fetch **`GET /api/assets/<signed-token>/<encoded-file-name>`**, exactly as returned in `relativeUrl`, resolved against the owning environment’s HTTP origin. It is a capability URL: the signature/expiry authorizes bytes, without an Authorization header. Signing TTL is normally one hour; consume returned `expiresAt`, because bucketing can affect particular assets. The HTTP route returns either stored file bytes or extracted tool image bytes. Invalid/expired URLs can return 404; remint once rather than looping. Do not persist signed URLs or use them as cache identity. [S12]

### Public MCP limits and PR #1 integration

`t3_thread_read({threadId,view:'activity',limit,afterPosition,maxCharsPerItem,itemId?,textOffset?})` returns `thread`, `recentRuns`, `items`, `nextPosition`, `hasMore`. Each item has `position`, `visibility`, `sourceThreadId`, `itemId`, `runId`, `messageId`, provenance, `type`, `status`, `title`, `text`, `textTruncated`, `nextTextOffset`, `updatedAt`. **No `attachments`, structured tool `output`, image list, or asset URL field exists.** Dynamic-tool data is JSON-stringified into `text`; sometimes a reference can be recovered, but this is neither complete nor a typed media transport, and text truncation makes speculative parsing unsafe. [S13]

Public MCP attachment tools upload/send attachments; they do not provide the missing read/download API. `EnvironmentAuth.rejectMcpClientAudience` explicitly rejects MCP client sessions outside `/mcp`, including authenticated HTTP and WebSocket upgrades. “Full access” MCP does not turn the token into an environment token. Signed asset URLs are an exception only because they independently authorize a resource: anyone already holding one can fetch it without MCP credentials. [S14]

PR #1’s `T3McpBackend.thread()` constructs text-only messages from `t3_thread_read`; its optional `legacy` field is currently used for approvals/review. Add capability reporting and media methods to `T3Backend`. If legacy credentials exist, fetch legacy media descriptors for the relevant source IDs and use legacy asset minting. Avoid doubling the full transcript on every poll; request descriptors/details on demand and cache them. If MCP-only, render available text and say “Images require a legacy connection on this T3 version.” Do not silently ask an agent to export files or send another message just to populate the UI.

## 2. Minecraft 26.3 rendering

Verified classes and signatures are from the supplied decompilation, not older Yarn examples. [M1–M4]

- `com.mojang.blaze3d.platform.NativeImage`: `read(byte[])`, `read(ByteBuffer)`, `read(InputStream)` validate a PNG header before STB decoding. **JPEG must not be passed directly to this API**, despite STB’s general JPEG support. Use it for validated PNG. For JPEG use JDK ImageIO; optionally TwelveMonkeys JPEG for extended variants. For WebP bundle `com.twelvemonkeys.imageio:imageio-webp` and required core/common modules, a pure-Java ImageIO decoder under BSD-3-Clause. Preserve SPI service registrations when packaging. Test the selected pinned release on the game JVM. [M1, E1]
- Decode to a bounded `BufferedImage`, then allocate `new NativeImage(width,height,false)` and copy ARGB values with `setPixel(x,y,argb)`. `setPixelABGR` expects a different packing. Apply JPEG EXIF orientation when provided. First-frame-only GIF/WebP is acceptable for v1, explicitly labelled if animated. SVG/HTML/PDF are file cards, not raster decodes.
- `net.minecraft.client.renderer.texture.DynamicTexture(Supplier<String>, NativeImage)` creates and uploads the GPU resource. Register with `Minecraft.getInstance().getTextureManager().register(Identifier, texture)`, using `net.minecraft.resources.Identifier` (not `ResourceLocation`). Perform registration/upload/release on the Minecraft client/render execution path, never the HTTP decoder worker.
- `Screen.extractRenderState(GuiGraphicsExtractor, int, int, float)` draws the panel in 26.3. Use `net.minecraft.client.gui.GuiGraphicsExtractor.blit(RenderPipelines.GUI_TEXTURED, identifier, x,y,0f,0f,drawWidth,drawHeight,pixelWidth,pixelHeight,pixelWidth,pixelHeight)`; the explicit source size prevents accidental cropping when scaling. Retain aspect ratio and letterbox. Optional linear filtering requires the correct sampler; default `DynamicTexture` uses nearest filtering.
- `DynamicTexture.setPixels(newImage)` closes the previous native image but **does not recreate the GPU allocation**. Reuse/upload only at unchanged dimensions. Recreate and replace a registered texture when dimensions change. `TextureManager.release(id)` removes/closes it; do not separately close the same owned image. Do not release resources still referenced by an extracted GUI frame; queue eviction at a safe frame boundary. [M2, M3]

### Layout and ownership

Replace the current assumption that every conversation row is a fixed-height `T3Markdown.Line`. Introduce a conversation block model: `TextBlock`, `ImageBlock`, `FileBlock`, `HtmlBlock`, with measured pixel height and stable key. Keep markdown wrapping for text. Build prefix sums for scroll offsets/visible-block lookup; reserve aspect-ratio placeholder space before download, preserve scroll anchoring, and invalidate layout when dimensions arrive. Add thumbnail hit regions to `T3Screen`; a click opens `T3ImageScreen` with fit-to-window, pan/zoom, close/Escape, dimensions and Open original. Scissor inline drawing to the conversation pane. Do not fetch/decode during `extractRenderState`.

`T3State.Message` must preserve media descriptors as well as role/text. Maintain ownership/reference counts for textures used by both the conversation and viewer. Cancel or ignore old callbacks using an environment/thread generation counter after switching accounts/threads. Avoid duplicate thumbnails for attachment and Markdown references to the same resource.

### Proposed limits (client policy, not T3 guarantees)

- Two download/decode workers; at most two active decodes and one queued browser frame. Request images only for visible blocks plus one screen of prefetch.
- Compressed raster fetch cap 10 MiB by default, enforce while streaming even without `Content-Length`. Read dimensions before allocating; reject dimensions over 8192 on either axis or 16 megapixels total, using checked arithmetic. Decode/downsample before creating native/GPU copies; avoid a full 16MP Java raster when the reader supports source subsampling.
- Inline decoded thumbnail maximum 1024 px on the longest edge; full viewer maximum 2048 initially, with an explicit higher-quality action subject to budget/device maximum. LRU budgets: 64 MiB GPU images, 64 MiB retained native pixels; transient Java decoder memory additionally bounded to 64 MiB per decode. A native RGBA copy and GPU RGBA copy each cost `4*w*h`; a 2048² texture is 16 MiB in each domain, before decoder buffers. These limits are independent of Java heap usage.
- Disk cache: 256 MiB LRU, seven-day age default, original compressed images only, atomic temp-file rename. Key by environment identity + attachment ID, or source thread/item/image index + revision; workspace images require `fileRevision`/content hash. Never key by signed URL. Separate accounts and invalidate on credential removal; provide Clear image cache. Do not disk-cache live browser frames. Persist no authorization headers or signed URLs.
- Release evicted native/GPU resources, cancel downloads on screen/account closure, bound full-screen pinning, and retain text/error cards when decoding fails. Resource reload must rebuild or explicitly invalidate runtime texture entries.

## 3. The collaborative browser API

### Discover tabs, then attach to the existing page

Over the existing RPC socket:

- **`preview.list({threadId})`** → `{sessions,serverEpoch,revision}`.
- **`subscribePreviewEvents({})`** → stream of `opened`, `navigated`, `resized`, `failed`, `closed`; events carry `threadId`, `tabId`, `createdAt`, `serverEpoch`, `revision`, and snapshots or event-specific data. It is a global subscription: filter by thread. Subscribe/buffer before list, then reconcile by epoch/revision to avoid races. This is metadata, not pixels.
- Snapshot fields: `threadId`, `tabId`, `navStatus` (`_tag`, URL/title for relevant states), `canGoBack`, `canGoForward`, optional `viewport`, `colorScheme`, `zoomFactor`, `profileId`, `runtime:'desktop'|'server'`, `headless`, `automationOwner`, `reveal`, `revealRequest`, `updatedAt`.
- Read/list/subscription require **`orchestration:read`**. `preview.open`, `.resize`, `.adjust`, `.close`, `.clearProfile`, `.reportProfiles`, `.reportStatus` require **`preview:operate`**. Do not use report APIs from a viewer to impersonate the desktop runtime. [S15]

Stream:

```text
POST /api/auth/websocket-ticket/media
Authorization: Bearer <environment token>

GET ws(s)://<environment>/api/preview-stream/ws
    ?threadId=<id>&tabId=<id>&wsTicket=<ticket>
    &maxWidth=1280&maxHeight=800&quality=70&interactive=false
```

The media ticket endpoint returns `{ticket,expiresAt}`. Use a fresh ticket on reconnect as necessary; the contract distinguishes reusable media tickets from RPC tickets. Do not send the long-lived bearer in a query string. Stream auth requires `orchestration:read`; inputs additionally require `preview:operate` and `interactive` not equal to `false`. Query defaults: 1280×800, JPEG quality 70; server clamps requested maxima to 7680×4320 and quality to 100. Client limits should be much smaller. [S10, S16]

**Wire format:** each binary message is one compressed JPEG, not a video codec stream. Assemble fragmented WebSocket messages with a byte cap. JSON messages use `type`, including `viewport:{width,height}`, `control:{canOperate,controller,generation,dialog}`, `pointer`, `clipboard`, `download`, `fileChooser`, `fileChooserClosed`, `popup`, `probe`. Send `{"type":"ack"}` after consuming a frame. Server retains one in-flight frame and the newest pending frame, acknowledges superseded frames internally, and disconnects if its socket buffer exceeds 8 MiB. The CDP implementation paces ACKs at 100ms and emits a still for idle/settled pages: expect roughly 10 fps pacing, not guaranteed 60 fps. Motion can use lower resolution/quality, followed by a sharper still. No audio channel is present. [S16, S17]

Start observe-only. On explicit Take control, reconnect with interactive enabled, send `{"type":"takeControl"}`, and wait for a control event whose `controller` is `you`. Other values are `agent`, `another-viewer`, `unclaimed`. Use `releaseControl` when leaving interaction. Taking control affects what the agent can do; show the owner state, and do not race the agent with inputs.

Input JSON supported on that same socket:

```json
{"type":"mouse","action":"down","x":120,"y":80,"button":"left","buttons":1,"clickCount":1,"modifiers":0}
{"type":"mouse","action":"up","x":120,"y":80,"button":"left","buttons":0,"modifiers":0}
{"type":"wheel","x":120,"y":80,"deltaX":0,"deltaY":100,"modifiers":0}
{"type":"key","action":"down","key":"Enter","code":"Enter","keyCode":13,"modifiers":0}
{"type":"key","action":"up","key":"Enter","code":"Enter","modifiers":0}
{"type":"text","text":"Unicode text"}
{"type":"navigate","url":"https://example.com"}
{"type":"history","delta":-1}
{"type":"reload"}
{"type":"dialog","accept":true,"promptText":"optional"}
```

Mouse `move` and middle/right buttons are supported too. Map GLFW keys/modifiers to CDP semantics, not numeric GLFW values; CDP bitmask is Alt=1, Control=2, Meta=4, Shift=8. Use committed text insertion for Unicode and avoid also inserting the same characters through key events. Map coordinates from the letterboxed destination rectangle into the latest **viewport CSS dimensions**, not JPEG dimensions (which can change during motion). Clamp and ignore clicks outside the image. Release pressed keys/buttons on focus loss, relinquish control on close. Server also releases input on viewer disconnect. Optional upload/download routes are `/api/preview-stream/upload` (POST, `threadId`, `tabId`, `chooser`) and `/api/preview-stream/download` (`threadId`, `tabId`, `id`); defer those UI features until core mirroring is stable. [S16, S17]

Close codes: `4404` tab gone, stop; `1012` reconnect, relist and retry with backoff; `4503` setup needed, JSON reason `{need:'sandbox'|'libraries',command}`. Show the supplied guidance, do not run host setup commands automatically. Disconnect the viewer when hidden instead of keeping expensive background decode/screencast work alive.

### Desktop versus server runtime: important nuance

`ServerBrowser.findTab` first checks an already-attached tab, then looks for the requested ID among `runtime:'server'` snapshots. `createTab` may connect that tab to an existing desktop page through `DesktopBrowserChannel` and Playwright CDP, or launch headless Chromium. Consequently, a tab displayed in the desktop app can still be streamable; `headless:false` is not a reason to reject it. Conversely, arbitrary pure desktop-runtime tabs are not guaranteed to be attachable. If unavailable, show Open in T3/Open URL and explain that the current tab cannot be mirrored. Do not migrate/reopen an active tab automatically: that can lose cookies, forms, and agent state. [S18]

Public MCP tools are not a substitute for this client API: `t3_preview_list` has only cursor/limit, derives its thread from `requireThreadMcpCapability('preview')`, and does not accept an outside client’s thread ID. Preview automation likewise requires an agent running in T3. The public-client rejection is covered by a server test. There is no public MCP frame subscription or browser viewer-ticket tool at this tag. [S19]

### Client implementation and cost

Use one `T3PreviewSession` per visible viewer, one network thread, one serial decoder and one texture. Start at 960×600 or 1280×800; cap client presentation at 10 fps. ACK after the frame is accepted/presented (or intentionally discarded), not after enqueuing into an unbounded pipeline. Reuse same-size texture storage; safely replace on resolution changes. On a stalled decode keep the previous image with a reconnect/loading indicator. Preserve tab ID across navigation; reset on tab closure or environment change.

1280×800 RGBA is about 3.91 MiB per CPU or GPU copy. Ten full uploads per second move about 39 MiB/s of raw pixels, excluding JPEG decode and GPU-driver overhead. This is a calculation, not a measured benchmark. Network bandwidth is compressed frame size × frame rate and depends heavily on content. Streaming keeps the same cookies, JS state and agent actions, with JPEG loss, round-trip input latency, limited frame rate and no audio. It reuses T3’s browser process; headless browser installation/setup may still be required on the T3 host if not already available. The Minecraft component itself only adds an image decoder and networking.

## 4. Alternatives

### MCEF / WebDisplays

The official MCEF repository documents Fabric/NeoForge, macOS 11+ Intel and Apple Silicon, LGPL-2.1, a native java-cef/CEF downloader, and Chromium 116 for its documented release. Official Modrinth API inspection found newest listed release `2.1.6-1.21.4`; Fabric JAR is 224,205 bytes. **No published Minecraft 26.3 Fabric artifact was found.** Existing platform support is not proof that its rendering/native integration works with 26.3. A fork/port and native lifecycle testing would be separate work. [E2, E3]

The tiny mod JAR does not include the browser: downloader fetches a platform archive from `${host}/java-cef-builds/${java-cef-commit}/${platform}.tar.gz`. Exact current macOS-arm64 archive size could not be verified: a HEAD request for the referenced build returned HTTP 403. Do not advertise an exact install size. Budget hundreds of MB for Chromium/native installation as a planning estimate, then measure the chosen distribution before promising a download size. MCEF is LGPL-2.1; preserve its notices and meet distribution/modification obligations, plus CEF/Chromium/java-cef third-party notices. Keep it an optional dependency rather than copying its source into the mod. [E2, E4]

WebDisplays creates interactive in-world web screens and requires MCEF, illustrating the browser-to-texture/input approach. It does not supply a 26.3 compatibility guarantee or access to T3’s live page. [E5]

Directly loading a T3 preview URL in MCEF creates a **different browser**: separate cookies, local storage, JS heap, DOM and forms; localhost refers to the Minecraft host, not necessarily the T3 host. Navigating to the same URL does not mirror the agent. It can provide better local animation and browser features after a port, but introduces native downloads, Chromium processes, more memory/CPU/GPU load, lifecycle complexity and another browser update surface. Do not choose it for the requested minimal-setup mirror.

### System browser

Use the platform URI opener already used by the mod, with an HTTP(S) URL obtained from the tab snapshot or a newly minted signed HTML asset. Label “Open URL externally” so it is clear this opens a separate session. A T3 thread link is a better fallback when the aim is to view the existing collaborative tab in T3. For remote localhost URLs, require an existing forwarded/public URL; never assume `localhost:3000` means the same machine. This has negligible added mod download size and implementation effort, but leaves Minecraft and cannot reproduce agent session state.

## 5. Upstream requests

To make public-MCP-only setup complete, request explicit APIs rather than relaxing token audience isolation:

1. Add structured `attachments` and `media` to `t3_thread_read` (including source thread/item, stable ID, MIME, byte count, dimensions, ordered tool-image index and revision), or add a paginated `t3_thread_media_list(threadId,…)`. Include inherited timeline ownership correctly. Keep base64 out of ordinary transcript text.
2. Add an authorized read-only MCP asset resolver: attachment/tool-output/workspace-image reference → short-lived signed `relativeUrl`, `expiresAt`, dimensions/revision. Restrict it to resources the caller can read. Existing signed HTTP assets already solve byte delivery.
3. Add outside-client preview list with explicit `threadId`, plus a scoped viewer-session mint tool returning stream URL/ticket/expiry, streamability, runtime, capabilities and permitted interaction. Separate read-only viewing from preview operation consent. Continue enforcing ownership; do not allow MCP tokens wholesale on `/ws` or `/api/*`.
4. Document/version the viewer JSON protocol and publish per-tab `canStream`/`canControl`/reason. Extend it to pure desktop-runtime tabs if desired via the existing desktop broker; retain page identity rather than reloading URLs.
5. Add a final `html_render` thumbnail/capture asset (with width/theme/revision) and optionally interactive viewing through a managed preview tab. HTML bytes alone cannot be rendered by Minecraft’s raster GUI.

No upstream change is required for the first legacy-backed image release or for mirroring existing streamable tabs. Public MCP-only parity and pure desktop-runtime coverage need upstream support.

## 6. Commit-by-commit implementation plan

1. **Media model and capabilities.** Extend `T3Backend`/`T3State` with immutable media references and explicit image/browser capabilities. Preserve message IDs/attachments in `T3Protocol`; add lazy tool detail retrieval and source-ID handling. Keep MCP-only limitations explicit. Tests: attachment-only messages, inherited items, duplicate message projections, omitted tool output, text-only MCP.
2. **Legacy asset client.** Implement `assets.createUrl` over `T3Socket`, same-origin signed fetch, bounded HTTP bodies, one remint on expiry, cancellation and environment separation. Add optional legacy media adapter in `T3McpBackend`. Tests: image ordinal with text blocks before it, expired URL, wrong environment, 404/missing bytes, auth removal.
3. **Decoder and bounded texture cache.** Pin/package TwelveMonkeys WebP, JPEG ImageIO path, PNG validation, dimension/subsampling policy, memory/disk LRU and texture ownership. Tests: PNG alpha, JPEG orientation, lossless/lossy WebP, oversized/malformed headers, eviction/disconnect. Verify packaging preserves ImageIO readers.
4. **Inline image blocks and viewer.** Implement variable-height block layout, placeholders, thumbnails, error/file/HTML cards and `T3ImageScreen`. Manually validate GUI scale, scroll anchoring, resizing, very tall images, account switches and repeated viewer close/open. Confirm native/GPU memory returns to budget after eviction.
5. **Observe-only browser mirror.** Add preview list/event reconciliation, media ticket mint, JPEG/JSON WebSocket parser, ACK/backpressure, one-frame queue and one visible texture. Handle tab lifecycle/close codes and pure-desktop fallback. Test fragmented messages, slow decoder, resize/motion-size changes, ticket expiry, reconnect, idle page, headless and desktop-backed server tab.
6. **Explicit browser control.** Add Take/Release control, owner badge, CSS coordinate mapping, mouse/wheel/key/Unicode events and focus cleanup. Test agent handoff, competing viewer, readonly scopes, letterboxing, modifier shortcuts and dialog handling. Keep file upload/download/clipboard features separately scoped.
7. **Fallbacks, settings and acceptance checks.** Add HTTP(S) external opener, thread link fallback, resolution/fps/cache settings and capability explanations. Measure game frame time, decoder CPU, network rate and native/GPU memory on macOS arm64 with the installed T3 build. Verify that hidden viewers stop work and a browser stream never writes a screenshot for every frame.
8. **Optional future MCP adapter.** Implement upstream media/list/ticket APIs once released, capability-gated by advertised tools/contracts. Do not add MCEF to this sequence; evaluate it in a separate port/prototype only if independent in-game browsing becomes a product requirement.

Acceptance: raster images render with correct proportions/colors; no render-thread network/decode stalls; no unbounded allocations; live view follows the same tab; clicks reach the correct CSS location only under explicit control; MCP-only users receive a truthful supported fallback. No runtime performance or full desktop-tab coverage claim is accepted until measured.
